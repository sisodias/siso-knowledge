# Tests asserting source structure, not just runtime behavior

**Claim**: Write tests *about the source code* as a separate category from lints and runtime tests. Example: assert that no file exceeds 350 lines. Assert that Zod schemas are deduplicated across packages. Assert dependency edges between architectural layers.

**Why it matters**: The codebase adapts itself to the harness. Long files blow context windows. Duplicated schemas force the agent to reason twice. These aren't behavioral bugs — they're *context efficiency* bugs. A regular lint doesn't catch them; a runtime test doesn't care. So you need a third category of verification that speaks about the shape of the code.

**Example assertions worth writing**:
- File size ceilings (e.g., 350 lines)
- One canonical implementation per primitive (async helper, retry wrapper, parser)
- No forbidden cross-layer dependencies (front-end imports of server-only code)
- All network calls wrapped in retry+timeout
- Every public API has a matching test file

**Error message discipline**: Failing assertions must emit remediation prompts, not just "fail." Not "type error on line 42" — instead "you have an `unknown` here because we parse-don't-validate at the edge; replace with the Zod-inferred type."

**For SISO**: We don't have this third test category anywhere. Worth adding for repos where workers frequently diverge from conventions. Could start simple: a `scripts/verify_shape.py` that agents run before declaring completion.
